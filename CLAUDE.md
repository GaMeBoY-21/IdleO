# GPU Rental Platform: project memory for Claude Code

## How we work
Read docs/WORKFLOW.md before every task. You are the builder: build, run all tests, commit, and report in the format the prompt asks for. Prompts live in docs/prompts/.

## What we are building
A peer-to-peer GPU marketplace for India. Hosts (people with RTX gaming laptops and desktops) rent out GPU time by the minute; renters (students, developers, small startups) run AI jobs on them. Cloud gaming comes later, and only for legally cleared titles. Full plan: docs/plan/execution-plan.md and docs/plan/technical-design.md. The PDFs beside them contain the diagrams.

## Current phase
Phase 1 (compute core: batch jobs end to end, built to production standard; free credits until the company and payment partner exist). Phase 0's hardware runs wait for a borrowed Windows RTX laptop; Phase 1 work that needs no GPU goes ahead now. The web app is built in rounds, each reviewed by Nikki before the next: foundations and the renter's home first, then booking, then the host side.
Do NOT build yet: real payments, gaming runtime, notebooks or endpoints, multi-region.

## Architecture rules (never break these)
1. Nothing at home is exposed: agents dial out over gRPC with TLS; host services listen only on the overlay network.
2. Every session is a lease: batch 2 minutes, endpoint and game 10 minutes, renewed every 30 seconds, never longer than the renter's reserved credit. An agent stops work when its lease lapses.
3. Database first, then side effects: commit the state change and an outbox row in one transaction, then send messages.
4. Everything is idempotent: commands carry a command_id; APIs that create things take an Idempotency-Key header.
5. Two witnesses for money: bill a minute only if the agent reported it AND the control plane saw the lease alive.
6. Least privilege: containers run non-root, read-only root, no host mounts, all capabilities dropped, LAN egress blocked.
7. Reuse proven open source for hard problems: Tailscale/Headscale, Sunshine/Moonlight, Docker, Pingora.
8. Compatible by default: .proto changes are additive only; the control plane supports the last three agent releases.

## Quality bar
We are building the final product, not an MVP (ADR 0006). Every piece meets this bar from the start:
- No temporary hacks or dead features.
- Tests: unit, integration (Testcontainers), contract and end-to-end, plus failure drills.
- Security: mTLS, short-lived tokens, secrets never in code, signed releases, rate limits.
- Data: Flyway migrations and restore-tested backups.
- Operations: metrics, logs and traces, with an alert and a runbook for every user-facing failure.
- Delivery: CI on every change, staging, one-click deploy and rollback.
- Web app: a real design system, accessible and mobile-friendly, with proper loading, error and empty states.

## Conventions
- Money is integer paise (Java long, Rust i64, SQL bigint). Never floating point. In Java, money is the shared kernel's Paise type, whose arithmetic throws on overflow.
- Money moves only through billing's Ledger.post: one balanced transaction of two or more entries, with the wallet cache updated in the same database transaction. txn_id is derived from what caused the posting, so a retry is a no-op. Ledger entries are never edited or deleted; a correction is a new reversing transaction. The database enforces balance, append-only and non-negative wallets, and a test fails if anything but Ledger writes billing.ledger_entries or billing.wallets (ADR 0014).
- Charging (ADR 0017), rules every change must keep:
  - A minute is charged only when the agent reported it AND the control plane's own lease record (sessions.lease_coverage) has one unbroken stretch covering the whole minute, both from the same attempt. Coverage never comes from anything the agent says; minute k of an attempt starts at its first RUNNING as the control plane received it, plus k minutes.
  - A started minute both witnesses saw is charged as a whole minute. A minute only one witness saw is never charged; it goes to metering.review_minutes.
  - Metering settles every 15 minutes from minute 0 and at the end, through billing's SessionCharges, never past the spending cap or the hold plus the available balance. txn_id is a name-based UUID of the session and window number; a settlement's claims and posting are one transaction under the session's row lock.
  - Every hold change goes through CreditReservations and lands in the append-only billing.reservation_changes; the nightly check adds them up.
  - A lease is renewed only while the hold, less what's committed, covers the minutes it would start. Running out is a StopSession with checkpoint_first, never a negative wallet.
  - A lost attempt's minutes ending after its newest complete checkpoint (storage's marker time, never the agent's clock) are waived; settled ones are refunded once, txn_id a name-based UUID of the session and attempt, in the original proportions.
  - Directions: metering reads sessions (MeteredSessions) and agentgateway (UsageReports), and charges through billing; sessions declares SessionCosts and metering implements it. Nothing depends on metering. Billing asks hosts who owns a host (HostOwners).
- IDs are UUIDv7. Times are UTC (timestamptz). Never trust agent clocks for billing; every "now" comes from an injected clock.
- Control plane: Java 25, Spring Boot 4, Spring Modulith, built with Maven through ./mvnw (ADR 0008). One Spring Modulith module per bounded context (identity, hosts, agentgateway, overlay, scheduling, sessions, metering, billing, payouts, trust, notifications). Modules talk only through public APIs or events and never read another module's tables.
- Database: PostgreSQL 18 with Flyway migrations, expand then migrate then contract. V20 and V21 drop columns in the same step that copies them, which is safe only because no real data exists yet; once real data exists, a migration adds first and removes in a later release. One schema per module; Flyway owns all DDL. Persistence is Spring Data JDBC with explicit SQL (JdbcClient where needed), no JPA (ADR 0009). Valkey 9 (Redis-compatible, via Spring Data Redis) only for state that is allowed to expire, and never in readiness. Only the agentgateway module writes host presence, always conditional on the connection that owns the record (ADR 0011); others ask whether a host is online through the hosts module's HostPresence port, which agentgateway implements, so the dependency never points back from hosts (ADR 0013).
- Migrations name the schema of every object they create or change (identity.users, never users). Flyway's default schema is flyway, so an unqualified name lands there silently; a test fails if any table other than Flyway's history table appears in the flyway schema.
- API errors use RFC 9457 Problem Details, and go only through the catalog (ADR 0019): every error is `ApiProblem.of(Problem.X, detail)`, its `type` `/problems/<slug>` from the one enum `Problem`. A test fails if a `ResponseStatusException` or a bare `ProblemDetail` is built anywhere else, or if any test gets a problem without a catalog type; `docs/api/problems.md` and the clients' copy `api/problems.json` (slug, status, title) are generated from the enum (`./mvnw test -Dtest=ProblemCatalogTests -Dproblems.write=true`), and a test fails when either drifts. Slugs never change once published; another person's resource is `not-found`, never a 403.
- Browsers call /v1 only from the origins in web.allowed-origins, with a bearer token and never cookies; production refuses *, plain HTTP and localhost (ProductionSettingsGuard).
- Module directions (ADR 0015): sessions publishes SessionRequested and SessionCancelled, and scheduling listens; scheduling reads hosts (SchedulableHosts), sessions (SessionBookings), presence (AgentPresence) and holds credit (CreditReservations), and queues agent messages through agentgateway's AgentCommands; agentgateway declares the OfferReplies port and scheduling implements it. Events are durable (Spring Modulith's JDBC registry, table modulith.event_publication, created by Flyway). Never add a dependency back from hosts, billing, sessions or agentgateway to scheduling.
- Hosting (ADR 0023): an owner can pause a host (until a time within 7 days, or until they resume; it ends by itself, no sweep), rename it and remove it (409 `host-busy` while it runs a session; otherwise its row stays, because the ledger points at it, its certificates are revoked, its stream closes and it answers 410 `host-removed`). `CandidateFinder` stays the one place the scheduler's filters live: it skips paused hosts, and offers a session only when free disk less the listing's `keepFreeGb` (10 to 500, default 20) still covers it. A host and its owner see a running session's service, its time and what the host has earned, never the renter, their inputs or their parameters. The host's earnings are read only from the ledger's `host_payable` entries (`HostEarnings`, `GET /v1/earnings`), so they always equal it; `EarningDetails` (billing declares, metering implements) only labels them. Telemetry is the latest heartbeat plus a ring of 60 one-minute points in Valkey, for the owner's screen only, never for billing. The price band comes from scheduling (`GET /v1/hosts/{id}/price-band`: other active hosts with the same GPU model, trimmed by 10% each end, or `scheduling.price-band-defaults` below 3 hosts).
- Uploads (ADRs 0019, 0022) go straight to storage through pre-signed multipart links, never through the control plane: a folder of up to 1,000 files or one file, 40 GiB at most, each file at uploads/{id}/files/{path}, kept in the renter's My files until 30 days after a session last used it. The web app remembers each part's ETag in IndexedDB, so choosing the same files again resumes the upload. Each of a session's named inputs is an upload (staged by the agent's supervisor into input/{name}/, paths kept, before minute 0) or an https URL the job fetches inside its sandbox. The agent never fetches a renter's URL.
- We provide the GPU; renters bring their own model, data and code (ADR 0022). No template may supply a model: every template takes the renter's model, data or code as its inputs.
- A session's live view is one Server-Sent Events stream (GET /v1/sessions/{id}/events) for every client, built by the same SessionViews as GET; a change sends a hint after commit through ValkeyHints (the one pub/sub pattern, shared with command delivery), and each stream also re-reads every 5 s, so Valkey is never required. `settled` is the one definition of "nothing will change any more".
- Logs: the agent's sink uploads chunks to attempt-{n}/logs/{seq}.log and reports latest_log_seq; the control plane only ever raises it and never lists storage for logs.
- Everything sent to an agent goes through agentgateway.agent_commands; Valkey pub/sub is only a hint, and a sweep delivers anyway. The one exception is LeaseRenew, sent every 30 s straight down a live stream through agentgateway's AgentStreams, only by the instance holding it.
- Sessions (ADR 0016): sessions depends on agentgateway and implements its ports SessionCredentials (fresh storage grants at each StartSession delivery; no credential is ever stored or logged), SessionStatuses and SessionReconciliation. Object storage is sessions.storage: MinIO (STS) locally and in tests, Cloudflare R2's temporary credentials in prod. A checkpoint or the outputs count only once the control plane finds their _COMPLETE marker in storage. A host counts as lost only sessions.leases.transit-allowance after lease_expires_at, so two attempts never run at once.
- Only the hosts module issues or reads host certificates and enrolment codes; other modules go through its public API (ADR 0010). Agents trust only our own root CA, and the gRPC port trusts only our root for client certificates (ADR 0011).
- Create requests take an Idempotency-Key through the shared IdempotentRequests helper, with a <schema>.idempotency_keys table in each module.
- A template's inputs, plain questions (presets, basic parameters, GPU memory), parameters, budget chips and GPU sizing are described once, in templates/catalog.yaml (ADRs 0019, 0022), served by GET /v1/templates, and checked by one validator (SessionParams) that booking and quoting share; every surface's form, flags and arguments are generated from that. Parameters reach the job only as SESSION_PARAM_<NAME> environment variables; never secrets. The test profile reads templates/development.yaml, whose services include catalog.yaml's offered ones word for word (a test fails if they differ), each with one simulated template.
- Access (ADR 0024): while `identity.invite-only` is true (the default; false in tests), a new user is `waiting` and may call only `GET`/`PATCH /v1/me` and `POST /v1/me/activate`; everything else is 403 `invite-required`, decided once in `IdentitySecurityConfiguration`. Invite codes (`IDLE-7K2Q-9XMD`) are single-use and stored only as a hash (`InviteCodes`), made by the `create-invites` operator command (docs/runbooks/invites.md); every try counts, 5 an hour per user, then 429 `too-many-attempts`; a wrong, used or expired code is one answer, `invite-invalid`. `signInMethods` on `GET /v1/me` comes from the token each time and is never stored. Notification choices (`GET/PUT /v1/me/notifications`, the notifications module's table) are all on by default and only departures are stored; the six money and safety kinds are locked on (422 `notification-locked`), and the kinds and their words are `NotificationKind`, the web app's only source for them.
- API keys and the renter limits (ADR 0025): a bearer value starting `idleo_` is an API key, checked in the one resolver in `IdentitySecurityConfiguration`; anything else is an ID token. A key is shown once (`IdempotentRequests.executeShownOnce` never stores it; a repeat is 409 `secret-shown-once`) and kept as a SHA-256 hash. `KeyRules` is the one list of what needs a browser sign-in (creating keys, approving CLI sign-ins, adding, removing or pricing a machine, its enrolment code, notification choices) and keeps `read` keys to GET; a full key may list and revoke its owner's keys. The CLI's key comes from device sign-in (`/v1/cli-logins`, RFC 8628 shaped; codes and poll tokens stored hashed). Requests: `limits.requests-per-minute` per person (or address) in Valkey (`RequestLimits`, 429 `rate-limited` with Retry-After; event streams once, log reads with a cursor free; Valkey down lets requests through). Sessions: `sessions.limits.*` counted in PostgreSQL in the booking transaction (`SessionLimits`: 429 `too-many-new-sessions`, 409 `too-many-sessions`). Every 429 says when to retry through `ApiProblem.retryAfter`.
- The renter CLI (ADR 0025, cli/, Rust): the binary `idleo` (its name is `BIN_NAME` in src/brand.rs), built from its own workspace with the agent's gates (fmt, clippy pedantic `-D warnings`, `cargo test`, `cargo deny` with permissive licences only: so no `dirs` crate, which pulls MPL-2.0). Its API types are generated from api/openapi.yaml by build.rs (typify), never committed, and `tests/api_contract.rs` lists every call it makes. The key comes from `IDLEO_API_KEY`, else the keychain, else a 0600 file (`IDLEO_NO_KEYCHAIN=1` skips the keychain); the API address from `--api`, `IDLEO_API_URL`, else the local stack. Exit codes are the plan's table (0 to 7; anything it doesn't name is 1), from the problem type (`Exit::for_problem`). A booking's Idempotency-Key and an unfinished upload's parts are kept in the config folder until done; Ctrl-C during `run` detaches and never stops the session.
- Tests: JUnit 5 and Testcontainers for Java, cargo test for Rust. New behaviour ships with tests.
- Secrets never go in code or git; use a gitignored .env locally. Never ask for passwords or keys.
- Real personal data lives only in the gitignored private/ folder, never in commits, fixtures or tests.
- Sunshine and Moonlight are GPL-3.0: never copy their code into this repo.
- Web app (ADR 0018), rules every change must keep:
  - Every screen follows web/DESIGN.md and has its four states: loading (a skeleton exactly the content's height), empty, error with a retry, and stale. Zero axe violations, and no layout shift (CLS 0).
  - Money is formatted only by formatPaise (web/src/lib/money.ts), from integer paise, never floating point, never optimistically.
  - The sign-in SDKs (firebase, oidc-client-ts) are imported only inside web/src/auth/; a lint rule enforces it. Our code never stores a token.
  - Colours, sizes and durations come only from web/src/design/tokens.ts (the accent from web/src/brand/); a lint rule refuses raw colours and arbitrary values.
  - The budgets (web/README.md: LCP 2.0 s, INP 200 ms, CLS 0, TBT 150 ms, 150 KB first-load JavaScript, accessibility 100, on Lighthouse's mobile profile) are never loosened without Nikki's say; if one can't be met, stop and report it with numbers.
  - The local sign-in adapter is for local builds only; a staging or production build refuses it (web/src/build-settings.ts).
  - A service's booking screen is generated from its template in the catalog (web/src/features/book/steps.ts, params.ts), never written by hand per service; its GPU memory rule mirrors the server's (web/src/features/book/vram.ts).
  - Session state comes only from the query cache, which the session screen's event stream (web/src/api/useLiveSession.ts, writeSession) and the lists' polling fill; no component keeps its own copy. A screen polls a session only while its stream is down.
  - Every problem type and every code a session can end with has words: web/src/lib/problems.ts (a test checks it against api/problems.json) and web/src/lib/labels.ts ENDINGS (a test reads the control plane's and the agent's sources). A new type or code needs its words in the same change.
  - The Hosting screens (ADR 0023, web/src/features/hosting/) follow the same rules: an owner's money is only what the server last returned (a machine's "earned so far" is read again every 5 s while it runs a session, never counted up on the client); the 20% fee is mirrored once, in web/src/lib/hosting.ts, with a test; a pause's choices become times in India there too; a machine is never shown with a renter's name; the code to enrol a host lives only in the page's memory. Their invented data is web/e2e/fixtures-hosting.ts, whose figures are sums of its entries (src/test/hosting-fixtures.test.ts).
  - The invite step and Account (ADR 0024, web/src/features/invite/, web/src/features/account/): any request that meets `invite-required` sends the person to `/invite/` from the one place every query passes (`src/api/invite-required.ts`), never from a screen's own check, and marks the cached account waiting; an invite code is shown in groups by `src/lib/invite.ts`; a notification switch moves only after the server has saved it, and a locked kind is on and disabled with the server's reason; Account's notification choices come last on the page, so their skeleton moves nothing below it. Its invented data is `meWaiting` and `notificationChoices` in web/e2e/fixtures.ts.
  - API keys and approving a CLI sign-in (ADR 0025, web/src/features/account/ApiKeys.tsx, features/cli-login/): the new key is held only in `CreateKey`'s own state (never the query cache, never storage; its mutation is reset the moment it has the answer) and is shown once with Copy and "You won't see it again"; revoking asks first in a sheet that names the key; the CLI approval page draws whole from the start (the code is in the link), so only the device's name arrives later and nothing moves. Their invented data is `apiKeys`, `newApiKey` and `pendingCliLogin` in web/e2e/fixtures.ts.
  - Requests a screen doesn't need to paint its main content start after that paint (useAfterPaint), and the frame's shared modules stay in one chunk (web/vite.config.ts): every request before the first paint counts against the budgets.
