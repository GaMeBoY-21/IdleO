# Commands

Every command for building, testing and running the project, moved here from CLAUDE.md word for word. `scripts/check-changed.sh` and `scripts/check-all.sh` (below) are the checks to run.

Control plane, run from control-plane/ (needs Java 25 and Docker):
- ./mvnw verify: compile with -Werror, enforcer, all tests (Testcontainers, modularity), Spotless check, JaCoCo report
- ./mvnw spotless:apply: fix formatting
- scripts/dev-ca.sh: create the throwaway development CA under the gitignored private/dev-ca/ (--force to replace it; --server-ip ADDRESS issues just the server certificate again with that address too, for ./start.sh --lan), and beside it the admin console's TOTP key and the codes' HMAC key (admin-totp.key, invite-code.key, both kept across --force)
- scripts/run-local.sh: run locally against compose.yaml's PostgreSQL and the dev CA; loads .env, always uses the local profile, refuses any prod profile; signs people in through the development sign-in server unless given --real-sign-in, which trusts your own Identity Platform project from .env (docs/runbooks/identity-provider-setup.md)
- Java code for proto/ is generated during the build (target/generated-sources); never commit it
- api/openapi.yaml is the API contract, generated by springdoc from the controllers (ADR 0018). ApiContractTests fails verify when it drifts; after an intended API change, run ./mvnw test -Dtest=ApiContractTests -Dopenapi.write=true and review the diff. Record fields are required in it unless @Nullable

Renter CLI, run from cli/ (Rust; the toolchain is pinned in cli/rust-toolchain.toml; cli/README.md):
- cargo fmt --all --check; cargo clippy --all-targets -- -D warnings (pedantic is on); cargo test (unit tests, and tests/api_contract.rs against ../api/openapi.yaml); cargo deny check (permissive licences only)
- `idleo docs --markdown` (hidden) prints the command reference; docs/site/generated/cli.md is its committed copy, and a test fails when it drifts (`IDLEO_DOCS_WRITE=1 cargo test docs_reference` rewrites it)
- cargo build --release, then target/release/idleo --help; IDLEO_API_URL and IDLEO_CONFIG_DIR point it at a stack and a config folder, IDLEO_NO_KEYCHAIN=1 keeps its key in a file; scripts/e2e/agent-online.sh builds it and drives it (sign in, the simulated fine-tune, a cut-off upload resumed, outputs downloaded, keys made and revoked, sign out)

Python SDK, run from sdk/python/ (uv; Python 3.12 pinned in .python-version, `requires-python >= 3.10`; sdk/python/README.md):
- uv sync; uv run ruff format --check . && uv run ruff check .; uv run mypy idleo (strict on the hand-written layer); uv run pytest (unit tests against a fake API and storage, the contract test, the docs drift test)
- uv run python scripts/generate.py rewrites idleo/_generated/ after an API change (`--check` fails on drift, as CI does); uv run python scripts/docs.py rewrites docs/site/generated/sdk.md after a change to a public call or its docstring (`IDLEO_DOCS_WRITE=1 uv run pytest tests/test_docs.py` does too)
- scripts/e2e/agent-online.sh installs it (`uv sync --locked`) and runs scripts/e2e/sdk-gate.py in the CLI scenario, signed in with the key the CLI has just stored: the gate example with the simulated fine-tune, its logs followed live, the adapter downloaded and its size checked against the outputs list

Host agent, run from agent/ (Rust; rustup installs the toolchain pinned in rust-toolchain.toml):
- cargo fmt --all --check
- cargo clippy --workspace --all-targets -- -D warnings: pedantic is on for the whole workspace; allow a single lint only with a comment saying why
- cargo test --workspace: unit tests, and integration tests against an in-process mutual-TLS control plane
- cargo deny check: permissive licences only (no GPL in the agent) and RustSec advisories
- cargo run -p agent -- run --fake-gpu [--fake-gpu-model NAME --fake-gpu-vram-mb MB] [--fake-free-disk-mb MB] [--dev-runner]: run on a Mac with invented GPUs (needs agent.toml and an enrolment; see agent/README.md), by default "IdleO Fake GPU" with 12,282 MB; --dev-runner, only with --fake-gpu, runs sessions by simulating them against real object storage, and a template's `--simulate <kind>` (fine-tune, run-code) plays that service's log lines and generated outputs. Without a runner the agent declines offers
- Leases count on the LeaseClock (CLOCK_BOOTTIME on Linux, QueryPerformanceCounter on Windows, CLOCK_MONOTONIC on macOS), never std::time::Instant (ADR 0016)
- Rust code for proto/ is generated at build time by protox (agent-proto/build.rs), never by a system protoc; never commit it
- #![forbid(unsafe_code)] everywhere except the agent-windows crate, the one documented place for Windows API calls (ADR 0012)
- Never fall back to fake telemetry silently: fake GPUs only with --fake-gpu, and a missing NVML is an error
- The Windows app (agent/README.md, "The Windows app"): scripts/build-windows.sh [--release-keys] cross-builds the five programs on the Mac with cargo-xwin and Homebrew's llvm and lld into dist/windows/ (IDLEO_SETUP_* set where setup points, IDLEO_APP_VERSION the version); scripts/checks/agent.sh also runs `cargo xwin clippy --target x86_64-pc-windows-msvc` when cargo-xwin is installed (it says so when it skips) and `cargo deny --config deny-windows.toml check` beside deny.toml (which leaves out the tray's and setup's Linux backends). Their tests run on the Mac against fakes (`release`'s `fakes` feature)
- The container runner (ADR 0035): scripts/build-distro.sh --dev and scripts/dev-distro.sh up|down|status|stop-distro|start-distro|refresh-runner|exec build and run the development distribution; scripts/images/publish.sh --dev [--cuda] pushes the job image to the local registry and writes private/local/development-real.yaml (--release --registry ghcr.io/OWNER/NAME pushes the one that ships and pins templates/catalog.yaml); agent/images/pytorch/test.sh [--dev] tests the image (lock.sh regenerates its lock files); agent/runner/tests/hostile/run.sh runs the 16 hostile tests against the development distribution; ./start.sh --real-runner runs the stack with real jobs (with --lan the Windows laptop runs them with the CUDA image); scripts/e2e/real-runner.sh is the end-to-end test (the hostile tests too, through the real path) (Run your code stopped, adopted after an agent restart, resumed after a lease lapse, and a tiny CPU fine-tune, through the CLI)
- Releases (ADR 0034): scripts/release/dev-key.sh makes the development key pair in private/release-dev/; scripts/release/new-release-key.sh the production one (public half to agent/release-keys/release.pub, private half only where you say); scripts/release/publish.sh --version X.Y.Z --rollout N [--dev] [--manifest-only] builds, Authenticode-signs (scripts/release/sign-windows.sh, the one TODO(signing)), zips, signs the manifest and uploads, files before manifest; --dev uses the dev key, local MinIO and private/release-dev/setup.env, and IDLEO_TEST_FAIL_TRIAL=1 with --dev builds a version whose trial never confirms
- scripts/install-report.sh [install id]: each install from the local database (COMPOSE_PROJECT_NAME picks the stack): minutes from setup_opened to listed, clicks, each step's duration, where it stopped

Everything at once, from the repository root (docs/runbooks/local-stack.md):
- ./start.sh: the whole system for local development (compose's containers, Grafana at :3300 with its Prometheus at :9190 and Alertmanager at :9193, alerts to Mailpit, the database archiving to MinIO and a first full backup, the control plane, two laptops' fake GPUs, the web dev server at :3000, the website at :3002, opened first), seeded idempotently (nikki@example.com ₹500 and owner of both laptops, nikki-low ₹1, nikki-broke ₹0, no invite step); logs in logs/, keys and pids in private/local/; Ctrl-C or --stop stops it all; --status, --fresh (asks), --real-sign-in, --link-demo (a third fake laptop that links by approval and prints its address), --lan (serve a Windows laptop on the same Wi-Fi: the API, website, web app, gRPC and storage on the Mac's LAN address, the server certificate naming it, a development release built for it and published to local storage (again whenever `agent/`, `proto/`, the image or the addresses have changed: `scripts/release/source-fingerprint.sh`, kept beside the version in `private/release-dev/published`), and each laptop's approval page opened on the Mac, since sign-in needs a secure page; docs/windows-laptop-test.md), --no-browser. scripts/e2e/start-check.sh checks it headless (CI runs it after the e2e)
- The sealed Linux image for Windows laptops (agent/distro/, README there): a Dockerfile from a digest-pinned Ubuntu 24.04, every Ubuntu package from the archive as it stood at `agent/distro/SNAPSHOT` (snapshot.ubuntu.com; `scripts/bump-distro-snapshot.sh` moves it forward monthly, with the pins and `VERSION`), with pinned containerd and NVIDIA container toolkit, no sshd, compiler or sudo, an `idleo` user, `wsl.conf` and `verify-lockdown.sh` (the one copy; phase0 reads them from here), and a runner placeholder. scripts/build-distro.sh makes `dist/idleo-distro-<version>.tar.gz` with its SHA-256 and manifest (a `TODO(signing)` hook); agent/distro/test.sh checks it (`--quick` skips the second build).
- scripts/check-all.sh [suite…]: every workflow's checks on this machine (agent, cli, control-plane, ops, drill, distro, proto, sdk, web, web-browser, e2e), with a summary; `--no-distro` leaves out the sealed Linux image's build (it needs Docker and a few minutes), `--no-drill` the restore drill; the gate before every push, and while CI minutes are short. Each suite's steps are scripts/checks/<suite>.sh, which the workflows call too; change a check there, once
- The steps start.sh and the e2e script share are scripts/lib/stack.sh (and scripts/lib/real-sign-in.sh, also used by run-local.sh; scripts/lib/toolchains.sh, which finds the pinned Java, Node, pnpm and Rust, also used by check-all.sh): add a shared step there, never a copy in one script
- CI is costly: every workflow cancels a superseded run (concurrency); agent and cli run macOS and Windows only weekly and by hand; push once at the end of a round, after check-all.sh is green

End to end, run from the repository root (needs Docker, Java 25 and Rust; docs/runbooks/local-stack.md):
- scripts/e2e/agent-online.sh: the compatibility test. Starts the local stack (PostgreSQL, Valkey, MinIO, the development sign-in server, Mailpit, the control plane with templates/development.yaml, a 10 s lease and 60 s storage grants), enrols eight real agents with fake GPUs and the development runner (the eighth the small-disk host: the only 24 GB GPU, with 1,000 MB free beyond the 10 GB its owner keeps, never offered a session), checks the hosts go online, then runs four charged sessions side by side, one per host: 150 s charged exactly 3 minutes (6 paise; host +4, platform +2), a renter stop at ~70 s, a kill -9 mid-run (attempt 2 resumes, attempt 1's minutes after its checkpoint waived), and a 6 paise spending cap. Beside them, the simulated fine-tune: a small JSONL uploaded, fine-tune-simulated booked, and its adapter_model.safetensors downloaded and read. Once they're done it checks hosting (ADR 0023) on the same hosts: two renamed laptops, every other host paused, the cheaper laptop paused so the next session goes to the other, resumed so it comes back, a host's running session, telemetry and sessions it ran, and `GET /v1/earnings` equal to the ledger's `host_payable` entries. The run's own accounts are activated with invite codes it makes (`E2E_INVITE_ONLY=false` lets anyone in), and last come the account journeys (web/e2e/account-journey.spec.ts, the `account-journey` Playwright project): a new person signs in and is asked for an invite code, a wrong code is refused, the script's spare code lets them in, a code works once, and Account saves a name and a choice across a reload, shows the locked kinds locked, and signs out. Each scenario's emails are read from Mailpit's API (ADR 0026): the normal run's and the simulated fine-tune's "finished" with their charge, exactly one each; the spending cap's stop; the host loss's "went offline" to the owner, with no renter or session in it; nothing for the session its renter stopped. Then the renter CLI (cli/, ADR 0025): `login` approved with the account's token, `run fine-tune-simulated` with a model folder and examples followed live to the adapter, a cut-off 1.5 GB upload resumed, outputs downloaded and resumed, then the Python SDK (ADR 0030, scripts/e2e/sdk-gate.py) with the key the CLI stored: the same fine-tune run from `Client()` with a preset, logs followed live, waited to the end, the charge equal to the API's, the adapter downloaded and its size equal to the outputs list's, and the live problems raised as exceptions (`not-found`, `unauthenticated`, a usage error), then `keys create` and `revoke`, `logout`. The renter limits (ADR 0025) are lifted for the harness's own accounts (`LIMITS_*`, `SESSIONS_LIMITS_*`); the control plane's tests hold them. Then a person's own data (ADR 0037, web/e2e/privacy-journey.spec.ts, the `privacy-journey` project): the file of everything made by the job, emailed and downloaded; a message to support acknowledged by email with its number; the web journeys' renter, who owns a machine with unpaid earnings by then, told why they can't delete yet; deletion asked for by a person of its own after a fresh sign-in, confirmed from its email and cancelled from the next email's link; the database then holds a ready export, the request cancelled and the security log's rows. Then money in (ADR 0039, web/e2e/payments-journey.spec.ts, the `payments-journey` project): a person with no free credit gives their state, adds ₹500 through the fake Razorpay's Checkout by test UPI (the seconds from Pay to "added" reported), downloads the receipt, sees a payment fail and a slow confirmation say so, and asks for ₹200 back; the script then checks each payment credited once in its own bought lot with its receipt, books a session paid from bought credit alone, and opens a chargeback (Razorpay's documented `payment.dispute.created`, signed) that freezes ₹50; the admin journey approves the refund, reads the chargeback and reconciles the day (0 found), and the script checks the refund processed with a credit note, the report's give-back a never-expiring free lot, and the chargeback won and released. Last, the admin console (ADR 0027, web/e2e/admin-journey.spec.ts, the `admin-journey` Playwright project), which also answers that message from Tickets (one audit row, the answer emailed): the script makes a new person an admin with `grant-admin`, leaves one more host enrolled but pending and books a long run; in one page the journey sets up a second factor and reaches the dashboard, activates the host, grants ₹1.25 and finds it in the audit log, and force-stops the run once it has run past a minute, whose renter then (a browser of their own) rates it with one tap and a comment and reports a problem, after which the admin refunds part of the report (one more paisa than the platform's commission, so both parts show), the renter's session, credit and Reports show it, and the host's owner finds a "Refunded to renter" line in their earnings; the script then reads each action's one audit row (the refund's included), the report's refund and its one balanced ledger transaction, the earnings against the ledger, and the run's settlement (its charge net of the refund). Then money out (ADR 0040, a 40 s dispute window and a 20 s hold for the run; web/e2e/payouts-journey.spec.ts, the `payouts-journey` project, in two steps): the hosts' owner verifies a PAN and a UPI ID in the browser; Run now pays them (processed); a UPI ID whose payouts fail, one the bank reverses, then a good one, each paid once; a report refunded after its session was paid out, owed and recovered from the next earnings; Earnings shows it all and the statement downloads; a second host asks to delete their account and, under a legal order, is paid a final payout before the erasure; today's payouts reconciled with the fake RazorpayX (0 found); and the ledger's payout rules. It runs reconcile-wallets (0 mismatches), checks the hosts go offline, and tears everything down. CI runs it on every control-plane, agent, proto or template change
- scripts/e2e/agent-online.sh --keep-running: the stack to look at by hand, until Ctrl-C: two agents with laptops' fake GPUs (RTX 4060 Laptop, 8 GB, ₹7.20/h; RTX 4080 Laptop, 12 GB, ₹10.80/h), the web app at :3000 (E2E_SERVE_WEB=0 leaves the port to pnpm dev), and nikki@example.com (E2E_ACCOUNT) with ₹500; prints a ready curl with a fresh token
- The default run also builds the web app and runs its journeys on a fifth agent (web/e2e/journey.spec.ts: Home; from Home, Fine-tune a model with a generated 3-file model folder and examples, Quick, a budget chip, the server's ceiling and hold, live to the adapter, read; Run again from My files; an upload interrupted by a reload resuming from its last part; the small-disk host never offered a 24 GB session (and no-gpu-free from the API); not enough credit; a cancelled upload; the event stream dropping and coming back; stopping on a phone), and the booking contract on a sixth (ADR 0019): a 12 MiB file uploaded in 3 parts straight to MinIO, a quote, echo-input booked with params and that upload, followed on its event stream to settled, its logs, result.json's SHA-256 and params, the charge, and input-not-accepted, insufficient-credit and upload-in-use by type. Last, after the other scenarios, the hosting journeys (web/e2e/hosting-journey.spec.ts, the `hosting-journey` Playwright project): a machine added from its name to connected with a real agent enrolled from the code on the page (scripts/e2e/activate-host.sh does the operator's step), paused and resumed, its price changed and the quote's top price with it, an earning session read on the Hosting tab, Earnings and Sessions it ran against the ledger, and removed; before them, a small release signed with a key made for the run (the control plane trusts it through IDLEO_RELEASE_PUBLIC_KEY), older than the agents so none updates, shows Download for Windows on Add a machine and its link redirects to the setup program in storage. It also checks MinIO's CORS preflight for the web origin. --web runs the web app's browser checks instead of the charged scenarios
- Development-only behaviour is a setting, never a code path (for example agentgateway.allow-development-hosts, trusting the local sign-in issuer, sessions.storage.provider minio, or a sessions.templates.catalog other than the bundled one). Every new development setting must be added to ProductionSettingsGuard, which refuses to start the prod profile with any of them (ADR 0013)

Operations, run from the repository root (ADR 0036; docs/runbooks/monitoring.md, alerts.md, backups.md):
- scripts/checks/ops.sh: the alert rules (`promtool check` and `test rules` against ops/alerts/tests/), `mimirtool rules check`, both Alertmanager routings (`amtool`), the dashboards and the ops scripts; each tool is an image compose.yaml already pins
- scripts/ops/alert-drill.sh: on a stack of its own, the seconds from the control plane dying, and from archiving stopping (a 1-minute test window), to the alert's email in Mailpit
- scripts/ops/load-alerts.sh [--check]: loads ops/alerts and ops/alertmanager/production.yaml into Grafana Cloud with mimirtool, from MIMIR_* and ALERTS_* in the shell
- ops/backup/drill.sh [--runs N] [--keep]: the restore drill on a fresh stack (compose project idleo-drill), which also erases a person after the moment it restores to and proves reapply-erasures erases them again; restore.sh --to <time|latest>, verify-ledger.sh --container NAME, backup-now.sh [--container NAME], dev-key.sh [--force]

Operator commands, the control plane in the ops profile (runs once, starts no web or gRPC server, exits with 0 done, 2 bad command line, 3 refused, 4 a check found a problem; docs/runbooks/granting-credits.md, docs/runbooks/hosts.md):
- OPERATOR=<handle> java -jar control-plane.jar --spring.profiles.active=prod,ops grant-credits --user <id> --paise <n> --reason "<why>" --key <key>
- OPERATOR=<handle> ... reverse-grant --grant <id> --reason "<why>"
- OPERATOR=<handle> ... reconcile-wallets: the nightly wallet check, now; moves no money, and keeps its result for the admin console
- OPERATOR=<handle> ... grant-admin <email> --reason "<why>" and revoke-admin <email> --reason "<why>": the only way to make or unmake an admin; revoking and granting again is also how a locked-out admin gets back in, with a fresh enrolment (docs/runbooks/admin.md)
- OPERATOR=<handle> ... activate-host --host <id> --reason "<why>" and suspend-host --host <id> --reason "<why>" (docs/runbooks/hosts.md)
- OPERATOR=<handle> ... reapply-erasures: erases again every account on the erased list, in the database and in storage (ADR 0037); `ops/backup/restore.sh` runs it after a restore (`ops/backup/reapply-erasures.sh --port PORT [--jar FILE]`), `--no-reapply` skips it only to compare a restore with its moment
- `OPERATOR` is a short handle (letters, digits, `.`, `_`, `-`), never an email or a full name
- Locally: COMPOSE_PROJECT_NAME=idleo-e2e OPERATOR=<handle> ./mvnw -q spring-boot:run -Dspring-boot.run.profiles=local,ops -Dspring-boot.run.arguments="…", against the scripts/e2e/agent-online.sh --keep-running stack
- A module adds an operator command as an OperatorCommand bean in the ops profile; OperatorCommandRunner picks it by name; a command that takes a value after its name says so with operands()

Web app, run from web/ (Node 24.21.0 from .node-version, pnpm 12.9.1; web/README.md):
- pnpm install, then pnpm dev against E2E_SERVE_WEB=0 scripts/e2e/agent-online.sh --keep-running (copy env.local.example to .env.local; a build also needs VITE_STORAGE_URL, storage's origin, for uploads); sign in with any @example.com address
- pnpm typecheck, pnpm lint, pnpm test (Vitest), pnpm build (the app: static dist/ with pre-rendered frames, the CSP and dist/headers.json), pnpm build:site (the website, apart: dist-website/), pnpm size (the app's first-load budget, then the website's); pnpm serve (the app on :3000) and pnpm serve:site (the website on :3002)
- pnpm e2e, pnpm lighthouse and pnpm gallery need the stack and pnpm serve; scripts/e2e/agent-online.sh --web runs all the browser checks against a fresh stack, as .github/workflows/web.yml does
- The journeys (web/e2e/journey.spec.ts) need a real agent and a funded E2E_WEB_USER, so they run in scripts/e2e/agent-online.sh; pnpm lighthouse also runs the 10 MiB log test (web/e2e/performance.spec.ts)
- All invented screen data comes from web/e2e/fixtures.ts, whose figures are derived, not typed; src/test/fixtures.test.ts checks they add up
- API types come from ../api/openapi.yaml on every build, typecheck and test (src/api/schema.gen.ts, never committed)
- Visual baselines live in CI's visual-baseline artifact, not git; accept a change by running the web workflow with "update screenshots"
- The review gallery (pnpm gallery) goes to private/review/web-booking/ (GALLERY_DIR), with the last review's pictures from BEFORE_DIR beside the fixes; never committed
