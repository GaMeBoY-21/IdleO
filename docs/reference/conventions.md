# Conventions by area

The detail behind CLAUDE.md's rules, one section per area, moved here word for word. Read the section for the area you are changing.

## Money

- Money is integer paise (Java long, Rust i64, SQL bigint). Never floating point. In Java, money is the shared kernel's Paise type, whose arithmetic throws on overflow.

## The ledger

Money moves only through billing's Ledger.post: one balanced transaction of two or more entries, with the wallet cache updated in the same database transaction. txn_id is derived from what caused the posting, so a retry is a no-op. Ledger entries are never edited or deleted; a correction is a new reversing transaction. The database enforces balance, append-only and non-negative wallets, and a test fails if anything but Ledger writes billing.ledger_entries or billing.wallets (ADR 0014).

## Charging (ADR 0017)

Charging (ADR 0017), rules every change must keep:
  - A minute is charged only when the agent reported it AND the control plane's own lease record (sessions.lease_coverage) has one unbroken stretch covering the whole minute, both from the same attempt. Coverage never comes from anything the agent says; minute k of an attempt starts at its first RUNNING as the control plane received it, plus k minutes.
  - A started minute both witnesses saw is charged as a whole minute. A minute only one witness saw is never charged; it goes to metering.review_minutes.
  - Metering settles every 15 minutes from minute 0 and at the end, through billing's SessionCharges, never past the spending cap or the hold plus the available balance. txn_id is a name-based UUID of the session and window number; a settlement's claims and posting are one transaction under the session's row lock.
  - Every hold change goes through CreditReservations and lands in the append-only billing.reservation_changes; the nightly check adds them up.
  - A lease is renewed only while the hold, less what's committed, covers the minutes it would start. Running out is a StopSession with checkpoint_first, never a negative wallet.
  - A lost attempt's minutes ending after its newest complete checkpoint (storage's marker time, never the agent's clock) are waived; settled ones are refunded once, txn_id a name-based UUID of the session and attempt, in the original proportions.
  - Directions: metering reads sessions (MeteredSessions) and agentgateway (UsageReports), and charges through billing; sessions declares SessionCosts and metering implements it. Nothing depends on metering. Billing asks hosts who owns a host (HostOwners).

## IDs, times and clocks

IDs are UUIDv7. Times are UTC (timestamptz). Never trust agent clocks for billing; every "now" comes from an injected clock.

## Control plane

Control plane: Java 25, Spring Boot 4, Spring Modulith, built with Maven through ./mvnw (ADR 0008). One Spring Modulith module per bounded context (identity, hosts, agentgateway, overlay, scheduling, sessions, metering, billing, payouts, trust, notifications, privacy, support). Modules talk only through public APIs or events and never read another module's tables. Scheduled jobs run on a small pool (SchedulingConfiguration), so a job that waits on something slow holds only its own thread; one that runs past 20 s is logged by name.

## Database

Database: PostgreSQL 18 with Flyway migrations, expand then migrate then contract. V20 and V21 drop columns in the same step that copies them, which is safe only because no real data exists yet; once real data exists, a migration adds first and removes in a later release. One schema per module; Flyway owns all DDL. Persistence is Spring Data JDBC with explicit SQL (JdbcClient where needed), no JPA (ADR 0009). Valkey 9 (Redis-compatible, via Spring Data Redis) only for state that is allowed to expire, and never in readiness. Only the agentgateway module writes host presence, always conditional on the connection that owns the record (ADR 0011); others ask whether a host is online through the hosts module's HostPresence port, which agentgateway implements, so the dependency never points back from hosts (ADR 0013).

## Migration schemas

Migrations name the schema of every object they create or change (identity.users, never users). Flyway's default schema is flyway, so an unqualified name lands there silently; a test fails if any table other than Flyway's history table appears in the flyway schema.

## API errors (ADR 0019)

API errors use RFC 9457 Problem Details, and go only through the catalog (ADR 0019): every error is `ApiProblem.of(Problem.X, detail)`, its `type` `/problems/<slug>` from the one enum `Problem`. A test fails if a `ResponseStatusException` or a bare `ProblemDetail` is built anywhere else, or if any test gets a problem without a catalog type; `docs/api/problems.md` and the clients' copy `api/problems.json` (slug, status, title) are generated from the enum (`./mvnw test -Dtest=ProblemCatalogTests -Dproblems.write=true`), and a test fails when either drifts. Slugs never change once published; another person's resource is `not-found`, never a 403.

## Browser origins

Browsers call /v1 only from the origins in web.allowed-origins, with a bearer token and never cookies; production refuses *, plain HTTP and localhost (ProductionSettingsGuard).

## Module directions (ADR 0015)

Module directions (ADR 0015): sessions publishes SessionRequested and SessionCancelled, and scheduling listens; scheduling reads hosts (SchedulableHosts), sessions (SessionBookings), presence (AgentPresence) and holds credit (CreditReservations), and queues agent messages through agentgateway's AgentCommands; agentgateway declares the OfferReplies port and scheduling implements it. Events are durable (Spring Modulith's JDBC registry, table modulith.event_publication, created by Flyway). Never add a dependency back from hosts, billing, sessions or agentgateway to scheduling.

## The Windows app (ADRs 0033, 0034)

The Windows app (ADR 0033, ADR 0034): five programs from agent/ (`idleo-agent`, `idleo-hostd`, `idleo-launcher`, `idleo-tray`, `IdleO-Setup`), installed per user (programs `%LOCALAPPDATA%\Programs\IdleO\`, data `%LOCALAPPDATA%\IdleO\`, `HKCU` Run and Uninstall entries), never a Windows service and never elevated after WSL is on; `host.key` is SYSTEM plus the owner's SID. What setup, the launcher and the updater share is `agent/release`, one implementation each; new `unsafe` goes only in `agent-windows`. The tray and the launcher reach the agent over a named pipe only the owner can open, never a port. Releases are one Ed25519-signed manifest (`stable/latest.json` and `.sig`) in the `releases` bucket, no table and no admin API: the control plane serves it only if it verifies against `IDLEO_RELEASE_PUBLIC_KEY` and isn't older (`GET /v1/agent-releases/latest`, `/setup` a redirect; `no-agent-release` without one), offers `UpdateAgent` only to hosts in the rollout (`sha256(host_id‖version) mod 100 < rollout_percent`) that haven't rolled that version back, and the agent installs only when idle, after the new version's quick self-test, under the launcher's 5-minute trial. A normal build bakes the development key and refuses control planes ending `idleo.in`; `--features prod-keys` bakes `agent/release-keys/release.pub` and fails while it's empty; only `idleo-release sign --key` reads a private key. Owner activity (input, full-screen, unplugged, a GPU busy with something not ours) pauses within 2 s and stops a session checkpoint-first as `owner_returned`. The setup app's measurements are `POST /v1/host-installs/{id}/events` (no sign-in, nothing naming the person or machine), read by the admin Installs card and `scripts/install-report.sh`. A `reason` is a short code only (the server's `REASON` pattern; setup's codes are `agent/setup/src/reasons.rs`, whose committed list `api/install-reasons.json` the control plane's tests check, rewritten with `IDLEO_REASONS_WRITE=1 cargo test -p setup reasons`); the words behind a failed step or self-test check go in the optional `detail` (kept to 2,000 characters), which setup scrubs of the profile path, user name, computer name and hardware ids first (`scrub.rs`). Setup writes `%LOCALAPPDATA%\IdleO\logs\setup-<date-time>.log` (every step, command with exit code and output to 4 KB, the self-test JSON, any refused report); a release build's undo deletes it, a development build's keeps `logs`, shows where it is, and offers "Keep it for troubleshooting" (everything installed so far stays, no Run entry, launcher or link; running setup again offers Repair from the step that didn't pass). Setup tries a batch of measurements once, stops after 3 refused in a row, and a development build says "Couldn't report to IdleO: <status>". A development build's setup also runs `idleo-agent self-test --facts [--storage HOST:PORT]` (`agent/agent/src/facts.rs`; a release build collects nothing): WSL's version and networking mode, kernel, NVIDIA driver, CUDA version, host RAM, the WSL VM's memory, and TCP probes from inside the distribution to its gateway, one address in each common LAN range and storage. They are facts, never checks: a blocked LAN is expected and fails nothing. Setup sends them as `step = facts`, `outcome = passed` events (`facts_system`, `facts_network`), which `install-report.sh` prints under `facts:` and the admin card ignores.

## The container runner (ADR 0035)

The container runner (ADR 0035): jobs run in containers inside the sealed Linux distribution, started by `idleo-runner` (agent/runner/), a systemd service on a root-only Unix socket that the agent reaches with `idleo-runner attach` over `wsl.exe -d IdleO-* -u root --` (or `docker exec -i` in development); containerd with nerdctl and CNI, no Docker. `agent/jobcore` is the one definition of the line protocol (`{"v":1,…}`: hello, list, start, stop, lease, refresh, pull, cancel_pulls, forget, self_check; events state, logs, checkpoint, exited, pull), of storage, staging, logs and the failure codes; additive changes only. The runner owns an attempt (pull by digest, scratch ext4 loop disk at /work, staged inputs, container, log pump, checkpoint sweep, lease and max-runtime watch, outputs, logs flushed before `exited`), stops it when its lease lapses on its own clock, and keeps jobs running when the agent goes away; a restarted agent adopts them. The sandbox is `agent/runner/src/container.rs` and `agent/distro/sandbox.nft` (one nftables table, read back as `nft -j list table` and compared by content with what the file makes, in a network namespace of its own, before every start; any difference loads the rules once more and checks again, and only a match starts a job, else `sandbox_not_ready`): user 10001, read-only root, 1 GiB /tmp, caps dropped, no-new-privileges, default seccomp, limits from the template, a bridge per session, the home network, the gateway and the VM's own addresses unreachable, DNS only to the runner's forwarder on the session's own gateway (UDP/TCP 53 there and nowhere else on it; it forwards to four public resolvers), TCP 80 and 443, no IPv6, and the reserved, benchmarking and documentation ranges (192.0.0.0/24, 198.18.0.0/15, 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) beside the private ones. An out-of-memory kill is told from the order of containerd's own events (the container's cgroup is gone the instant it exits, so its counter can't be read after): the exit event is read from the same stream as the OOM event. `agent/runner/tests/hostile/run.sh` runs 16 hostile tests that must all pass, against the development distribution; `run.sh --host ID` runs them through the real path on a linked host (the hidden `hostile-test` template of `templates/development-real.yaml`, booked as the key's owner, the owner's other hosts paused meanwhile), with rows 11, 15 and 16 N/A and saying why (row 12 is read from the runner's `leftovers` check, which a development runner writes into each session's log, and which the runner's self-test runs too); .github/workflows/hostile.yml runs them on amd64 by hand and weekly. Images are pinned by digest in the catalog (no cosign for ours); the job image is `agent/images/pytorch/` (CUDA 12.8.1, PyTorch 2.11.0, `MIN_NVIDIA_DRIVER` in `agent/release/src/drivers.rs`) with the fine-tune (`finetune.py`) and Run-your-code (`run.sh`) jobs and the job contract (`SESSION_PARAM_*`, `SESSION_INPUT_<NAME>_DIR`, `SESSION_OUTPUT_DIR`, `SESSION_CHECKPOINT_DIR`/`SESSION_RESUME_DIR`, `SESSION_CHECKPOINT_INTERVAL`, SIGTERM then a grace, `/work/idleo-failure.json` of which only `invalid_input` is believed), written for renters in docs/site/writing-a-job.md. The agent pre-downloads the images `Welcome.prefetch_images` names when idle and unmetered, and stops the distribution after 5 idle minutes. A development distribution (`scripts/build-distro.sh --dev`, `scripts/dev-distro.sh`) is the same image for the Mac's own architecture (arm64: containers can't nest under Rosetta) with `/etc/idleo/development`, which lets a job run without a GPU and maps `registry.idleo.test:5000` to a plain-HTTP registry (compose.yaml's `registry`); a release distribution has neither. Real templates are in `templates/development-real.yaml`, never in `development.yaml` (whose services mirror the catalog's with one simulated template each); `# dev:` lines say what production changes. Every failure code the runner can report needs words in api/endings.json.

## Encrypted scratch, abuse and fair use (ADR 0038)

Encrypted scratch, abuse and fair use (ADR 0038): each attempt's scratch disk is a LUKS2 volume (`agent/runner/src/crypto.rs`, `cryptsetup` key by pipe, 1000 forced PBKDF2 iterations because the key is random) whose key lives only in the runner's memory, with no swap and nerdctl's job log linked onto it; a kernel that can't (the self-test's `scratch_encryption`) gets no jobs, `sandbox_not_ready`, never a plain disk (a development distribution only says so and makes plain ones). The honest limit is in every doc: a host with administrator rights can read a *running* job's memory, so "don't send secret data to community hosts". Abuse (`agent/runner/src/abuse.rs`, `dns.rs`, the data file `agent/distro/blocklist.json`, every entry with an https source, whose copy in the distribution is the runner's fallback, and a newer one is a signed file of its own delivered without a new distribution, ADR 0041, docs/runbooks/abuse.md): only a listed build's SHA-256 or a second look-up of a listed pool in the same session stops a session (`abuse_stopped`, the renter suspended, audit actor `abuse-watch`); a listed name, a first look-up, 5 minutes of dropped connections and mining-like numbers for 15 only flag, because a hash catches only an unmodified build and a guess must never stop an honest job. The list has no hashes yet (they come from official release pages, hashed and then deleted, never run or committed). The session's DNS goes to the runner's forwarder on its bridge gateway, which answers a listed pool NXDOMAIN and logs only blocked names. The trust module's review items (`trust.abuse_items`, `AbuseReviews`, `/admin/v1/abuse`): confirm, confirm and ban (a ban is refused like a suspension, the same plain sentence, lifted only by clearing its item with a typed reason; `OpenToHeldAccounts` keeps a held account's own data, export, deletion and support open), clear (reinstated and the session's charge refunded in one ledger transaction through `SessionRefunds`), note; `AbuseStops` alerts above 3 stops an hour. Behaviour numbers (`trust.behavior_samples`, 90 days) are for review only, never billed on or shown to a host. Fair use is `agent/runner/src/fair.rs`: per session, in `inet idleo_fair` (nftables `limit`, which drops, since the distribution has no `tc` and WSL's 6.1 kernel no TBF/HTB), 50 new connections a second (burst 100) and an upload of half the line's measured speed (`upload_cap_kbps`, set by `agent/agent/src/fair_use.rs`, floor 5 Mbit/s), the runner's own uploads exempt, shown to the owner on the machine page (`uploadLine`). The Terms are enforced on the API: a creating call marked `@RequiresAcceptedTerms` answers 403 `terms-not-accepted` (CLI exit 5, SDK `TermsNotAccepted`) until the person has accepted in a browser at `/agree/`; reading, stopping, pausing, removing and downloading stay open; a key can't accept. The web app: a suspended or banned account (`me.status === "suspended"` for both) sees only `HeldShell`/`HeldAccount` (`features/held/`, a lazy chunk) with its data, deletion and support; the booking screen's line under "Request a GPU" says hosts are people at home and links the Terms; the admin console's Abuse screen is `features/admin/Abuse.tsx`. Who is behind each `OPERATOR` handle is `private/operators.md` (git-ignored).

## Host linking (ADR 0032)

Host linking (ADR 0032, supersedes ADR 0011's code step for owners): the agent's `idleo-agent link` (`agent::link`, exit codes 0 linked, 2 denied, 3 expired, 4 network) asks `POST /v1/host-links` (no sign-in, `limits.host-links-per-hour` per address, production refuses a higher one) for a link and a poll token (stored as a SHA-256 hash), opens the web app's `/link/<id>/` page, and trades the token for a ticket at `POST /v1/host-links/{id}/ticket` once the owner approved. The owner approves (`@BrowserSignInOnly`, name and price in the same call, once, idempotent) or denies; a link expires after 10 minutes; an approval and a denial are audit rows. The enrolment code inside the ticket is issued at redemption, never stored in clear. A new host is pending unless `hosts.auto-activate` (default false, in `ProductionSettingsGuard`). `GET /v1/price-band?gpuModel&vramMb` suggests a price for a GPU that is not a host yet. `enrol --code` stays for operators. The base of the approval address is `hosts.link.web-app-url`.

## Hosting (ADR 0023)

Hosting (ADR 0023): an owner can pause a host (until a time within 7 days, or until they resume; it ends by itself, no sweep), rename it and remove it (409 `host-busy` while it runs a session; otherwise its row stays, because the ledger points at it, its certificates are revoked, its stream closes and it answers 410 `host-removed`). `CandidateFinder` stays the one place the scheduler's filters live: it skips paused hosts, and offers a session only when free disk less the listing's `keepFreeGb` (10 to 500, default 20) still covers it. A host and its owner see a running session's service, its time and what the host has earned, never the renter, their inputs or their parameters. The host's earnings are read only from the ledger's `host_payable` entries (`HostEarnings`, `GET /v1/earnings`), so they always equal it; `EarningDetails` (billing declares, metering implements) only labels them. Telemetry is the latest heartbeat plus a ring of 60 one-minute points in Valkey, for the owner's screen only, never for billing. The price band comes from scheduling (`GET /v1/hosts/{id}/price-band`: other active hosts with the same GPU model, trimmed by 10% each end, or `scheduling.price-band-defaults` below 3 hosts).

## Uploads (ADRs 0019, 0022)

Uploads (ADRs 0019, 0022) go straight to storage through pre-signed multipart links, never through the control plane: a folder of up to 1,000 files or one file, 40 GiB at most, each file at uploads/{id}/files/{path}, kept in the renter's My files until 30 days after a session last used it. The web app remembers each part's ETag in IndexedDB, so choosing the same files again resumes the upload. Each of a session's named inputs is an upload (staged by the agent's supervisor into input/{name}/, paths kept, before minute 0) or an https URL the job fetches inside its sandbox. The agent never fetches a renter's URL.

## What an upload must hold (ADR 0022)

What an upload must hold is the catalog's, per input (ADR 0022 addendum): `must_contain` (rules of file names with `any_of`, `max_depth` and the renter's `message`) for a folder, `accepts_extensions` with `not_accepted` for a file. Booking and quoting check an upload's files against them (`input-not-usable`, 422; a zip by the file names in its central directory, read by range, never the whole file); the booking screen applies the same rules from `GET /v1/templates` when the files are chosen, before a byte is sent, in the same words (`web/src/features/book/content-rules.ts`, whose fixtures are checked against the catalogs). A link isn't checked at booking: the job checks it.

## Renters bring their own model (ADR 0022)

We provide the GPU; renters bring their own model, data and code (ADR 0022). No template may supply a model: every template takes the renter's model, data or code as its inputs.

## A session's live view

A session's live view is one Server-Sent Events stream (GET /v1/sessions/{id}/events) for every client, built by the same SessionViews as GET; a change sends a hint after commit through ValkeyHints (the one pub/sub pattern, shared with command delivery), and each stream also re-reads every 5 s, so Valkey is never required. `settled` is the one definition of "nothing will change any more".

## Session logs

Logs: the agent's sink uploads chunks to attempt-{n}/logs/{seq}.log and reports latest_log_seq; the control plane only ever raises it and never lists storage for logs.

## Commands to agents

Everything sent to an agent goes through agentgateway.agent_commands; Valkey pub/sub is only a hint, and a sweep delivers anyway. The one exception is LeaseRenew, sent every 30 s straight down a live stream through agentgateway's AgentStreams, only by the instance holding it.

## Sessions (ADR 0016)

Sessions (ADR 0016): sessions depends on agentgateway and implements its ports SessionCredentials (fresh storage grants at each StartSession delivery; no credential is ever stored or logged), SessionStatuses and SessionReconciliation. Object storage is sessions.storage: MinIO (STS) locally and in tests, Cloudflare R2's temporary credentials in prod. A checkpoint or the outputs count only once the control plane finds their _COMPLETE marker in storage. A host counts as lost only sessions.leases.transit-allowance after lease_expires_at, so two attempts never run at once.

## Host certificates

Only the hosts module issues or reads host certificates and enrolment codes; other modules go through its public API (ADR 0010). Agents trust only our own root CA, and the gRPC port trusts only our root for client certificates (ADR 0011).

## Idempotent creates

Create requests take an Idempotency-Key through the shared IdempotentRequests helper, with a <schema>.idempotency_keys table in each module.

## Templates and the catalog

A template's inputs, plain questions (presets, basic parameters, GPU memory), parameters, budget chips and GPU sizing are described once, in templates/catalog.yaml (ADRs 0019, 0022), served by GET /v1/templates, and checked by one validator (SessionParams) that booking and quoting share; every surface's form, flags and arguments are generated from that. Parameters reach the job only as SESSION_PARAM_<NAME> environment variables; never secrets. The test profile reads templates/development.yaml, whose services include catalog.yaml's offered ones word for word (a test fails if they differ), each with one simulated template.

## Access (ADR 0024)

Access (ADR 0024): while `identity.invite-only` is true (the default; false in tests), a new user is `waiting` and may call only `GET`/`PATCH /v1/me`, `POST /v1/me/activate`, and (ADR 0037) the Terms, their own data, export and deletion, and support (`@OpenToWaitingUsers`, now identity's public annotation); everything else (a request that reaches no handler included) is 403 `invite-required`, decided once, after routing, by the handler reached (`@OpenToWaitingUsers`, checked by `AccessRules`), never by the path's spelling. Invite codes (`IDLE-7K2Q-9XMD`) and admin recovery codes are single-use and stored only as HMAC-SHA-256 under `identity.invite-code-key` (`IDENTITY_INVITE_CODE_KEY`; `CodeHashes`; prod refuses to start without it or with the tests' value; changing it voids every unused code), made by the `create-invites` operator command (docs/runbooks/invites.md); every try counts, 5 an hour per user, then 429 `too-many-attempts`; a wrong, used or expired code is one answer, `invite-invalid`. `signInMethods` on `GET /v1/me` comes from the token each time and is never stored. Notification choices (`GET/PUT /v1/me/notifications`, the notifications module's table) are all on by default and only departures are stored; the money and safety kinds are locked on (422 `notification-locked`), and the kinds and their words are `NotificationKind`, the web app's only source for them.

## Notifications and email (ADR 0026)

Notifications and email (ADR 0026): the notifications module listens, with durable `@ApplicationModuleListener`s, to `SessionSettled`, `SessionNeverRan`, `SessionLowOnCredit` and `AttemptLost`, all announced by sessions (metering tells sessions through the `SessionMilestones` port, so nothing depends on metering); it reads sessions through `SessionOutcomes` and `SessionCosts`, hosts through `HostOwners.ownerOf`, identity through `UserDirectory.verifiedEmail`, and implements identity's `UnreadNotifications` (the count on `GET /v1/me`). One message for each event (the dedupe key names it), decided by the person's choices at that moment (locked kinds always both); an email is claimed in its own transaction before it is handed to the one `EmailSender` (SMTP; Mailpit locally on 8025, the production provider later, docs/runbooks/email.md) and given back only if the mail server refuses it, so it is sent at most once. An owner's message never names the renter or the session. Emails have no images and no tracking, and their links are plain pages of the web app. The sentences for why a session ended are `api/endings.json`, read by the web app and shipped in the jar; money is `Rupees.format`, checked with `formatPaise` against `api/money-format.json`. `GET /v1/notifications` and `POST /v1/notifications/read` are the in-app list.

## API keys and the renter limits (ADR 0025)

API keys and the renter limits (ADR 0025): a bearer value starting `idleo_` is an API key, checked in the one resolver in `IdentitySecurityConfiguration`; anything else is an ID token. A key is shown once (`IdempotentRequests.executeShownOnce` never stores it; a repeat is 409 `secret-shown-once`) and kept as a SHA-256 hash. What needs a browser sign-in (creating keys, approving CLI sign-ins, adding, removing or pricing a machine, its enrolment code, notification choices) is marked on its handler with `@BrowserSignInOnly`, and `KeyRules` (run by `AccessRules`, a `HandlerInterceptor`, after routing) refuses it to a key and keeps `read` keys to GET (a read key may revoke itself, `@ReadKeyMayRevokeItself`); it decides by the handler a request reached, never the path's spelling, and fails closed: a key's write that reaches no handler is refused (`KeyRouteTests` tries every encoded spelling of every browser-only route). A full key may list and revoke its owner's keys. The CLI's key comes from device sign-in (`/v1/cli-logins`, RFC 8628 shaped; codes and poll tokens stored hashed). Requests: `limits.requests-per-minute` per person (or address) in Valkey (`RequestLimits`, deciding by the matched route; 429 `rate-limited` with Retry-After; event streams once; every log read counts, against `limits.log-reads-per-minute` (120) instead; Valkey down lets requests through; prod refuses any limit above application.yaml's, `ProductionSettingsGuard.PRODUCTION_LIMITS`). Sessions: `sessions.limits.*` counted in PostgreSQL in the booking transaction (`SessionLimits`: 429 `too-many-new-sessions`, 409 `too-many-sessions`). Every 429 says when to retry through `ApiProblem.retryAfter`.

## Public availability (ADR 0029)

Public availability (ADR 0029): `GET /v1/public/availability` (scheduling, no sign-in, in `signedOutCalls`) gives each GPU memory class (8, 12, 16, 24 GB) whether a host is online, the live price range an hour only from 3 hosts online, and the typical range (`scheduling.price-band-defaults`); never a host or a count. Worked out at most once a minute (`PublicAvailability`, `Cache-Control: public, max-age=60`), limited per address by `RequestLimits` like every call without a sign-in. `public-site.starting-credit-paise` is unset until a new account's credit is decided, and the pricing page says nothing while it is.

## The admin console's backend (ADR 0027)

The admin console's backend (ADR 0027): `/admin/v1/**` has its own security chain in identity (`AdminSecurityConfiguration`): an ID token (never an API key) of a user with the `admin` role, which only the `grant-admin` and `revoke-admin` operator commands change, plus a live admin session in the `Admin-Session` header, started by a TOTP code (RFC 6238; the secret AES-GCM sealed under `identity.admin.totp-key`) or one of ten one-time recovery codes (stored hashed), tied to the sign-in identity that made it, 30 minutes from its last use and never past 8 hours. Anything less is the 404 of a path that doesn't exist, never a 401 or 403; the role alone reaches only `/admin/v1/session` and `/admin/v1/second-factor`. The fifth wrong code in 15 minutes locks admin access until `revoke-admin` and `grant-admin`. Each module's admin controller lives in that module and calls the same service method as its operator command (`HostActivation`, `CreditGrants`, `InviteService`, `WalletReconciliation`), which writes one row through identity's `AuditTrail` in the action's own transaction into the append-only `identity.audit_log` (triggers refuse changes; the app's database user has no UPDATE, DELETE or TRUNCATE on it); certificate issues and revocations are audited too. Every admin action takes an `AdminReason` (5 to 500 characters); lists page with `AdminPages`. The dashboard's figures come from each module's `DashboardFigures` (identity declares it), so nothing depends on metering. A force stop is `operator_stopped` (the agent hears `STOP_REASON_ABUSE`) and settles like any stop; a review-queue minute is charged as a settlement of its own through `SessionCharges`, never past the cap or the credit, or waived.

## Ratings and reports (ADR 0028)

Ratings and reports (ADR 0028, the trust module): trust keeps its own `trust.ended_sessions` from `SessionEnded` and `SessionNeverRan` (which carry the renter, the last attempt's host and the times), so it never reads sessions' tables. A rating (`GET`/`POST /v1/sessions/{id}/rating`, 1 to 5 stars, a comment of at most 500) is the renter's, for a session that ran at least a minute, given within 7 days of it ending and changed within 7 days of being given, for the host of its last attempt; hosts declare `HostRatings` and trust implements it: the average over sessions that ended in the last 90 days, worked out once a day (`trust.ratings.refresh-cron`, into `trust.host_ratings`), never on each rating, with the count rounded down to a multiple of 5 (`countAtLeast`), on the owner's host only from 5 ratings; a host never sees who rated or a comment (only `GET /admin/v1/ratings` does). A report (`POST /v1/disputes`, Idempotency-Key, `trust.idempotency_keys`) is the renter's ended session within 7 days, one per session, ever (409 `report-already-open` while open, `report-already-made` once resolved); while open, billing's `PayoutHolds` marks that session's earnings `payoutHeld`. An admin resolves it once (`/admin/v1/disputes/{id}/refund` or `/no-refund`, a reason the renter reads, audited in the same transaction); a refund goes only through billing's `SessionRefunds`: at most what the session's own ledger entries say the renter paid net, from `platform_revenue` first and then the hosts' `host_payable` in proportion, one `dispute_refund` transaction whose txn_id is a name-based UUID of the report; host earnings label it "Refunded to renter". A session's `chargedPaise` is net of these refunds; its spending cap is not.

## The renter CLI (ADR 0025)

The renter CLI (ADR 0025, cli/, Rust): the binary `idleo` (its name is `BIN_NAME` in src/brand.rs), built from its own workspace with the agent's gates (fmt, clippy pedantic `-D warnings`, `cargo test`, `cargo deny` with permissive licences only: so no `dirs` crate, which pulls MPL-2.0). ## Money out (ADR 0040)

Money out (ADR 0040, docs/runbooks/payouts.md), RazorpayX in test mode only:
  - The payouts module owns RazorpayX (`RazorpayXClient`, only documented fields; its keys `RAZORPAYX_*`, apart from money in's), PANs, UPI IDs, payout records, tax and reconciliation; every posting is billing's, through its `HostPayouts` port (pending and available read from the entries and `billing.payout_holds`, never posted; `start`, `paid`, `returned`, `forfeit`). Nothing but notifications depends on payouts.
  - A session's earnings are pending for `legal.payouts.dispute-window` after its last charge and while a report holds them, then available. Mondays 10:00 IST (`payouts.weekly-cron`) everyone with an active UPI ID, a verified PAN and at least `payouts.minimum-paise` is paid once for all their machines; no "pay me now". `host_payable` → `payouts_in_flight` (net) and `tds_payable` in one transaction before RazorpayX is asked; `reference_id` and `X-Payout-Idempotency` are both our payout's id; processed → `payouts_paid`; failed, rejected, cancelled or reversed → back to the machines (reversed marks the UPI ID suspect). Webhooks at `POST /v1/payouts/razorpayx/webhook` (signed, once by event id, the payout fetched from RazorpayX); a poll and a resend back them up; `PayoutReconciliation` nightly at 03:45 IST must find 0 (`payouts.reconciliation.open`); `BalanceCheck` the day before payday.

A UPI ID is RazorpayX's Fund Account Validation, active and a name match of at least 80 or an admin's approval; confirming one needs a fresh sign-in, and a change holds payouts 48 hours with an email.
  - Tax deducted at source is `TaxDeduction`, every number from `legal.tds` (the section's name is a setting; the year's gross caught up once past the individual threshold); live keys are refused until `legal.tds.confirmed`. A report refunded after its session was paid out is a clawback (`billing.clawbacks`): the owner's balance first, the rest a `host_receivable` recovered before the next payout, never debited from a UPI ID; an admin may waive it into `chargeback_losses`. Earnings figures count only what sessions caused (`HostPayoutService.EARNING_REFS`).
  - Deleting a host's account isn't blocked by earnings: `PersonalData.waits` says what's paid when, and the erasure pays a final payout at once (`beforeErasure`); with no UPI ID payouts may go to, the host adds one or gives the earnings up in writing (`POST /v1/payouts/forfeit`). The tests' fake is `razorpay/FakeRazorpayX` (samples in `src/test/resources/razorpayx/`); the local stack runs it as `FakeRazorpayXServer` on :8092, its payouts steered by the UPI ID (`payoutfails@`, `reversed@`). The web app's screens are `features/hosting/Payouts.tsx` and `PayoutDetails.tsx` (`/hosting/payout-details/`), the admin's `features/admin/Payouts.tsx`, `Verification.tsx`, `Clawbacks.tsx` and `Tax.tsx`; their invented data is `web/e2e/fixtures-payouts.ts` and the payout parts of `fixtures-admin.ts`.

## Host quality (ADR 0041)

Host quality (ADR 0041): the host score is the hosts module's (`hosts.host_scores`, `HostScoreService`, `HostReliability` for the arithmetic), worked out nightly and after a host's session ends or loses an attempt, and read by scheduling only through `SchedulableHosts.Candidate`. Hosts declares `HostSessionResults` (sessions implements it from `sessions.attempts.lost_reason`: finished, or lost to the host; never a renter's stop, a failed job or `owner_returned`) and `HostTrustSignals` (trust implements it: upheld reports and the admin's flag); hosts never reads their tables and never listens to sessions' events. Cache is the heartbeat's `cached_images` (digests, at most 64, kept in presence) against the template's image digest. The owner sees `Reliability: Good / Fair / New` and what lowers it, never that an admin flagged the host; admins see the numbers (`AdminHost.score`). "Run self-test" is `SelfTestRuns` for the owner (`/v1/hosts/{id}/self-test`, `/self-tests`) and the admin (`/admin/v1/hosts/{id}/self-test`, `/self-tests`, with a reason, audited as `host.run_self_test`): one run at a time, not while offline or running a session, 6 in 24 hours; hosts publishes `SelfTestRequested` and the agent gateway sends `RunSelfTest`; the agent answers with a `SelfTestProgress` for each check and a `SelfTestReport` carrying the run id. Tables `hosts.self_test_results`, `hosts.host_scores` and `hosts.self_test_runs` are in the personal data map.

The signed blocklist (ADR 0041): `stable/blocklist.json` and `.sig` in the release bucket, signed with the manifest's Ed25519 key by `scripts/release/blocklist.sh` (`idleo-release blocklist`, `sign`, `verify-blocklist`, `upload`); its version is when it was issued (`2026-10-25T09:30:00Z`, or a plain date for the distribution's copy), so "newer" is a string comparison everywhere. The hosts module's release feed reads it every `hosts.releases.refresh-every`, caches it only if the signature verifies and it is not older (`Blocklists`, `BlocklistCached`), and the agent gateway sends `UpdateBlocklist` after Welcome to an agent whose `Hello.blocklist_version` is older, and to connected agents when a newer one is cached. The agent (`agent/agent/src/blocklist.rs`) uses it only if it verifies against the release key built into it and is newer, keeps the last good copy, and gives it to the runner (`Request::Blocklist`, once its distribution is up and before a session starts); the runner (`blocklist_store.rs`) verifies every list itself against the release key in its image (`/usr/local/share/idleo/release.pub`), whoever handed it over: the file and its signature come from the agent, are kept as the last good copy in `/var/lib/idleo/blocklist/current.json` and `.sig`, and the distribution's own copy ships signed (`blocklist.json.sig`, `scripts/release/sign-distro-blocklist.sh`, run by `build-distro.sh`); with no list that verifies the runner starts no job (`sandbox_not_ready`) and judges a running session's processes by the newest list each look. A flagged program's executable is hashed and the hash goes in the signal, so an admin who confirms the review can add that build (`trust.blocklist_additions`, `LearnedBuilds`, `POST /admin/v1/abuse/{id}/blocklist`, audited); the control plane never holds the signing key, so `export-blocklist-additions` carries them to where it is.

An admin who suspends an account says why (`identity.users.suspension_cause`: `host_misconduct` or `other`); for `host_misconduct` the payouts module (`AccountStandings.payoutsHeld`) makes no payout to it, final payout included, until the suspension is lifted, and everything else about being paid is as before.

## Renters' own images (ADR 0042)

Renters' own images (ADR 0042): the images module (`images.*` tables, `/v1/images`, `/admin/v1/images`) holds submissions, their checks and private registries' tokens (sealed by the shared kernel's `Sealer` under `images.registry-token.key`, opened only for the scanner's claim and a StartSession as delivered, never logged, deleted `legal.retention.registry-tokens` after last use). Own images are off in production until `images.enabled` is set (default false; the guard allows it only with every scanner limit set, its token and the registry key; off, the list says so, a submission is `not-found` and the `custom-image` template isn't offered). Only a renter with a verified PAN (billing's `VerifiedPans`) submits or books one (`verified-pan-required`). A reference naming an address, `localhost`, a dotless name or `.internal` is refused unless it's in `images.dev-registries` (production refuses any). The scanner (`scanner/`, Rust, its own suite) runs in its own container (Trivy pinned by digest, user 10001, read-only root, no capabilities, no database or storage keys, its own network) and reaches only `/internal/v1/scanner/**` on `images.scanner.port` with `images.scanner.token` (`ScannerAccess`: that port answers nothing else, the public port answers `/internal/` 404; every step after the claim names the claim). It never unpacks a layer: blobs are downloaded as they are into an OCI layout, read as streams through `scanner/src/tar.rs` with every size capped (unpacked bytes per layer and image, `..` paths and links out of the image refused), every ELF file in every layer hashed; Trivy reads the layout for vulnerabilities and secrets (a secret's file and kind only). The scanner reports facts; every verdict is `ImageJudge`'s (limits, cached digest, blocklist by hash), and the renter's words are `ImageVerdicts`'. A check that crashes, times out or loses its scanner `images.check-attempts` times is `failed` (`not_checked`), never a pass; nothing is ready until a blocklist has judged it. Scans are cached by digest with their ELF hashes, and a newer blocklist (`BlocklistCached`, and a sweep) judges them again; a newly blocked digest is `ImageBlocked`, which sessions (cancels unstarted sessions, `image_blocked`) and notifications (`image-blocked`, locked) hear. The `custom-image` template (`own_image: true`, no `image` or `args`) is booked with `imageId` (`image-not-ready`, `image-blocked`); the session stores the pinned reference; `SessionSpecs.ownImage` sends the renter's command with `/bin/sh -c` (`OwnImageJobs`) or the image's own, its working directory, `own_image`, `image_pull_timeout` and `image_size_bytes`; the host's disk need adds the image's two sizes. CUDA matching is `CandidateFinder`'s, by `CudaDrivers`, which reads `api/cuda-drivers.json` like the agent's `drivers.rs` (`min_nvidia_driver()`): one rule. The runner pulls a renter's own image only at the attempt's start (pre-download never), with its login in a 0600 Docker config on `/run` named by `DOCKER_CONFIG` to nerdctl alone and deleted after, within its time limit (`image_pull_timed_out`), reports progress as the session's `pull` events (heartbeats' `image_done_bytes`, the session view's `imageDownload`), doesn't count the download against `max_runtime`, and deletes the image when the attempt ends. The alert ImageCheckBacklog is `images_checks_backlog_seconds` over 30 minutes.

## Containers and the cluster (ADR 0045)
Every server-side part ships as an image from this repository, its bases pinned by digest, running as a fixed non-root user on a read-only root with OCI labels; the control plane's has no shell. One chart, `deploy/helm/idleo`, installs them all; an environment's values file sets only hosts, sizes, replicas, issuers and development's stand-ins, and the defaults are production's. Every pod and container keeps rule 6's settings, with requests and a memory limit (the chart's unit tests fail otherwise). In a cluster the control plane runs on the `cluster` profile as the application user, never Flyway's; a new table's migration grants `idleo_application` what it needs (ApplicationRoleTests). Agents reach the control plane on its own load balancer, never through the ingress. An operator command in a cluster is a pod (`scripts/k8s/ops.sh`), never a second JVM in a serving one.
