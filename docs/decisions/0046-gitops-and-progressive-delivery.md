# 0046. GitOps and progressive delivery

- **Status:** Accepted
- **Date:** 2026-10-30

## Context

ADR 0045 gave the server side images we can prove we built, one Helm chart and k3s. Deploying still meant someone running `helm upgrade` with the right tag. Nothing recorded what each environment ran, and nothing stopped a release that broke the API from taking all of production at once. Its secrets were made by a script on one machine (`scripts/k8s/secrets.sh`), with no way to keep staging's and production's anywhere reviewable.

Three things are wanted. A merge to main should reach staging with no one touching it. Production should change only through a pull request a person merged. A bad release should take a small share of traffic and be undone without anyone noticing it first. The real staging and production servers come later (S5). Everything is proven now on the Mac's k3d cluster, and in CI on the same cluster. Staging's and production's configuration is written and validated, ready for those servers.

## Decision

**Flux, from git, read only.** Each cluster runs Flux v2.9.6: its source, kustomize, helm and notification controllers. They are exported once with the Flux CLI's own image into `deploy/flux/gotk-components.yaml`, with each image pinned by digest, so an upgrade is a reviewed diff. A cluster follows its folder: `deploy/clusters/local`, `deploy/clusters/staging` and `deploy/clusters/production`. The repository is public, so Flux reads it over HTTPS with no token. Flux never writes to git: we don't use `flux bootstrap`, which commits. Bootstrapping is applying `deploy/flux` and the cluster's `flux-system/sync.yaml` once, with its age key as the Secret `sops-age`. From then on Flux keeps itself up to date from the same folder. Each cluster has three Flux Kustomizations, applied in order:

- `flux-system`: Flux and the cluster's own objects.
- `infrastructure`: `deploy/infrastructure`, which is cert-manager, Flagger and a small Prometheus. Staging and production add Prometheus's remote write.
- `idleo`: `deploy/apps/idleo`, shared by all three clusters, which holds the namespace, the chart's source and the HelmRelease. Each cluster's `idleo/` folder adds its values, its Secrets and `release.yaml`.

**The chart is a signed artifact, and every release is pinned by digest.** On every build of main, the images workflow publishes the chart to `ghcr.io/gameboy-21/charts/idleo` as an OCI artifact, versioned `<version>-<commit>`. It signs the chart with cosign keyless, as it signs the images. Flux's `OCIRepository` installs the chart only if its signature comes from that workflow on main, through GitHub's OIDC issuer. An environment's `release.yaml` pins the chart's digest, the commit (`images.tag`, which names the release) and each image's digest (`images.digests`), so the chart pulls `idleo-<name>@sha256:…` and nothing else. `scripts/checks/deploy.sh`, a required check, fails if staging or production pins anything by tag. `scripts/deploy/release.py` is the one tool that writes and copies these files. It resolves a commit's digests from GHCR anonymously.

**Secrets in git, encrypted with SOPS and age.** Each environment has one age key pair. `.sops.yaml` encrypts the `data` and `stringData` of every Secret manifest under `deploy/clusters/<env>/secrets/` for that environment's public key. Flux decrypts them in the cluster with the private key, and nobody else holds it. `scripts/deploy/age-key.sh <env>` makes a key pair, writes the public half into `.sops.yaml` and prints it. It never prints the private half. The local key is made once into `private/k8s/age/` and also kept as the repository secret `SOPS_AGE_KEY_LOCAL`, the one secret a workflow reads: the k8s and gitops workflows need it to decrypt development's stand-ins. Staging's and production's keys are made by the product owner on her own machine. Their private halves go only into the cluster and her password manager. The local Secrets, which used to be made by script at every `up.sh`, are now committed SOPS files: development's database passwords, the control plane's development CA and keys, and the local CA for the Gateway (`scripts/k8s/secrets.sh --make`). The deploy check fails on any Secret under `deploy/` that isn't encrypted for its environment's key, and it shows that it refuses a plain one. gitleaks still scans every commit.

**Promotion.** When the images workflow succeeds on main, its last job resolves that build's digests and verifies every one: each image with `scripts/images/verify.sh`, and the chart's signature with cosign. It then opens a pull request, "Deploy <short sha> to staging", that changes only `deploy/clusters/staging/idleo/release.yaml`, and turns on GitHub's auto-merge, so the pull request merges itself by rebase once the required checks pass. Production is the `promote` workflow, run by hand. It copies staging's release into production's, verifies it again, and opens "Promote <short sha> to production" with the commits between the two releases. A person merges it. Reverting that pull request rolls production back. One script opens both pull requests (`scripts/deploy/open-pull-request.sh`), and it closes an older one for the same environment as superseded. GitHub doesn't start workflows for a pull request opened with Actions' own token, which guards against loops. The script therefore starts the required workflows on the branch by `workflow_dispatch`, and their checks report on the branch's commit as a pull request's own would. The images workflow ignores pushes that change only `deploy/clusters/`, so a merged deploy never builds and deploys again.

**Canary releases with Flagger.** Flagger v1.45.0 releases the control plane through the Gateway API (`gatewayapi:v1`, on k3s's Traefik). Its chart is pinned by digest and its signature is checked against Flagger's own release workflow. Flagger copies the chart's Deployment to `idleo-control-plane-primary`, which serves, and scales the Deployment itself to zero. It makes the Services and the API's HTTPRoute, so the chart leaves those out when `canary.enabled` (production's default). A new release starts the Deployment again as the canary. The route's weights then move to 10%, 25%, 50% and 100%, one step every 2 minutes while every check passes, and at the end the canary is promoted. Each step checks three things:

- the share of the canary's API requests that answered 5xx stays below 1%;
- their 95th percentile stays below 800 ms;
- the session-start success rate over the last 10 minutes is no more than 10 points below the hour before. A start succeeds when the session reaches minute 0, and fails when it ends first because it timed out on its host or couldn't fetch its input. Fewer than 5 attempts give nothing to judge.

`threshold: 1` means one failed check stops the canary where it is: its weight goes no higher. At the next step, at most 2 minutes later, Flagger sends all traffic back to the primary, scales the canary down and marks it Failed. Flagger checks the threshold at the start of each step, so the rollback can't come sooner without shorter steps. On the Mac, a release failing 30% of its calls was held at 10% of the traffic and rolled back within 4 minutes of its canary starting. Flagger's load tester sends the canary one request a second from before its first step, so a quiet hour still gives it something to be judged by.

**An in-cluster Prometheus only for Flagger.** Prometheus v3.15.1 keeps 2 hours of data and is held to 256 MiB. It scrapes the control plane's meters, which are published in Prometheus's format on a port of their own, 9464 (`MetricsPort`, cluster profile only). That port answers only `GET /metrics`, the public port never answers that path, the network policy lets only this Prometheus reach it, and no route leads to it. Scrapes are not counted as API requests. Prometheus also scrapes Flagger. Production's meters still leave through OTLP to Grafana Cloud (ADR 0036). In staging and production, Prometheus remote-writes Flagger's `flagger_canary_*` series, and nothing else, to Grafana Cloud. There `ops/alerts`' CanaryFailed pages through the same routing as every other alert. The commit statuses come from Flux's notification controller: it posts each Kustomization's outcome back to the commit on GitHub, so a failed canary fails the `idleo` Kustomization's health check (a CEL check on the Canary's phase) and shows on the commit. Before Flagger notices a new release, the Canary still reads Succeeded, so the first status can be early. It is corrected at the next reconciliation, within 10 minutes.

**Mixed versions.** Weights move HTTP requests only. An agent's gRPC stream is long-lived on its own LoadBalancer Service (ADR 0045), which reaches both versions' pods by a label Flagger leaves alone (`idleo.in/control-plane`). During a canary, an agent that reconnects may land on either version, and the database is the new release's while the release before still serves. So the agent protocol and the database must work with both versions at once. Rule 8 already keeps `.proto` changes additive and supports the last three agent releases. `scripts/k8s/canary-test.sh` runs an agent built from the previous release, which is the commit the change is based on. That agent enrols, stays online through the canary and runs a booking to the end.

**Expand and contract.** The migration Job is Helm's pre-upgrade hook, so a release's migrations run before its canary starts. The canary then meets the new schema while the old version still serves, and a rollback leaves that schema in place. So a migration in a release must work with both that release and the one before. Additive changes ship any time. A column or table is dropped or renamed only in a later release, once nothing that runs reads it. `scripts/checks/migrations.sh` runs first in the control plane's required check and enforces this: a migration after V61 that contains DROP, RENAME or ALTER … TYPE fails unless its file carries `-- contract: <reason>, safe since <version>`. The check prints the rule when it fails.

**Proof.** `scripts/k8s/up.sh --gitops` puts the Mac's cluster under Flux from this repository on GitHub, at the branch and commit it runs on, so the branch is pushed first. The chart and images it releases are the tree's own, pushed to the cluster's registry. A chart built on a laptop has no signature from the images workflow, so that one source is left unverified. Signing it with a local key wouldn't help: Flux accepts a key's signature only from the public transparency log, and a laptop's chart doesn't belong there. Instead the canary test has the cluster's Flux verify staging's real chart with `deploy/apps/idleo`'s own verify block, and refuse it for another workflow's identity. Plain `up.sh` (Helm directly) stays for quick work, using the same committed Secrets. `scripts/k8s/canary-test.sh` (the `gitops` workflow, on pull requests touching `deploy/` and weekly) checks five things: staging's chart verified (and refused for another identity), a good release through every step to promotion, a bad release rolled back by itself, a refused migration and the previous release's agent. The bad release is the same control plane with `web.faults.server-error-percent=30`, which fails that share of API calls. It is development only, and the prod profile refuses it (`ProductionSettingsGuard`).

**What S5 adds.** The real clusters, and these with them:

- staging's and production's age keys, and their SOPS-encrypted Secrets (`idleo-database`, `idleo-control-plane`, `grafana-cloud-metrics` twice, `github-commit-status`);
- the Let's Encrypt issuers;
- the server's Traefik on ports 80 and 443;
- applying `deploy/flux` and `flux-system/sync.yaml` once on each server.

## Alternatives considered

- **Argo CD.** It has a richer interface, but it runs a server and a database of its own, and its progressive delivery (Argo Rollouts) replaces the Deployment with its own kind, so the chart would no longer be plain Kubernetes. Flux has no web interface, which suits one person who reads git anyway, its controllers are lighter on an 8 GB node, and Flagger works on the chart's own Deployment.
- **`flux bootstrap github`.** It commits Flux's manifests and needs a token that can write to the repository. Committing the same manifests in a reviewed pull request, and applying them once, gives the same result with no write access anywhere.
- **Flux's image automation (ImageUpdateAutomation) for staging.** It commits to git from the cluster, so it needs a write token in the cluster and its commits skip the required checks. A pull request from the images workflow goes through the same checks as any change.
- **A GitHub App or a personal token to open the deploy pull requests**, so their workflows start by themselves. Either is a credential kept in the repository's secrets that can write to it. Starting the required workflows by `workflow_dispatch` with Actions' own token needs none.
- **Sealed Secrets or an external secret store.** Sealed Secrets ties every secret to one cluster's controller key, and a rebuilt cluster can't read them. An external store (Vault, a cloud's secret manager) is another service to run or pay for. SOPS files are plain git, reviewable as diffs, and age keys are one line each.
- **Judging the canary on Traefik's meters.** That would be one place for every service, but Traefik names a Gateway API backend by its generated service name, which changes with Flagger's Services. The control plane's own `http.server.requests` has the route and the outcome, as the existing alerts use it.
- **The local cluster from a pushed OCI artifact of the working tree** instead of GitHub. It would work with uncommitted changes and need no push, but the cluster would not be managed as staging and production are. Plain `up.sh` serves quick work.

## Consequences

- Nobody deploys by hand. A change reaches staging within the length of the required checks after its merge. Production moves only by a merged pull request, and git always says what each environment runs.
- Every migration must work with the release before it, and the check enforces this for every migration after V61. Dropping a column takes two releases.
- During a canary, two control-plane JVMs run: 1 GiB more requested memory on the node for about ten minutes. Flux, Flagger, its load tester and Prometheus request about 0.5 GiB together. values.yaml has the sums.
- A failed canary leaves git asking for a release the cluster refused. CanaryFailed keeps paging, and the commit status stays failed, until it is reverted or fixed.
- Reverting a production pull request runs a canary of the release before, which takes about ten minutes, not an instant switch.
- The deploy pull requests run every required check, about 15 minutes of CI each, which is free for this public repository.
- The local age key is in GitHub's secrets. It protects only development's stand-ins (a development CA and passwords for a cluster on a laptop), and staging's and production's keys are never there.
- Open question: whether staging's few requests give the session-start check enough to judge. With fewer than 5 attempts in 10 minutes it passes, so only production's traffic really exercises it.
